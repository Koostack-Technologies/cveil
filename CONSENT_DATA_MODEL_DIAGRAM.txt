KEY DESIGN PATTERNS
═════════════════════════════════════════════════════════════════════════════════

1. DUAL KEYS
   - Every entity has both BIGSERIAL (internal) and UUID (domain)
   - Foreign keys reference UUIDs for deterministic projections

2. MASKING TYPES (on PURPOSE_REGULATION)
   - PLAINTEXT: No masking
   - HASH256: Cryptographic hash
   - REDACT_ALL: Remove entire value
   - REDACT_UP_TO_LAST_4: Keep last 4 chars (credit cards)
   - REDACT_LOCAL: Remove local part (email: hide before @)

3. APPEND-ONLY LEDGER (CONSENT_LEDGER)
   - No updates/deletes
   - Every consent action creates a new record
   - Timestamps ensure chronological ordering

4. AGGREGATE BOUNDARIES
   - FIELD: Entity → Field → Category (tree structure)
   - REGULATION: Regulation → Jurisdiction (many:many)
   - PURPOSE: Purpose → Regulation (with policy attributes) + Purpose → Category (policies)
   - SUBJECT: Subject → Consent Ledger (immutable history) + DSAR (key management)

5. MULTI-TENANCY
   - Every table includes tenant_id VARCHAR(255)
   - Unique constraints include tenant_id (UNIQUE (tenant_id, name))
   - Postgres RLS isolation at runtime
