Authentication & Security

API keys, OIDC with DPoP, role-based access control, rate limiting, and tenant isolation.

Authentication Methods

Cveil supports three authentication methods:

1. API Keys

Tenant-scoped API keys for programmatic access. Keys are SHA-256 hashed on the server — the raw key is only shown once at creation.

Format cveil_ prefix for tenant keys, opr_live_ for operator keys
Header Authorization: Bearer cveil_your_key_here
Created via POST /api/v1/iam/me/tokens

2. OIDC (OpenID Connect)

Keycloak-based authentication for dashboard users and SSO.

Login POST /api/v1/iam/login
Returns JWT access token + refresh token
Expiry Access tokens expire in 5 minutes; refresh tokens in 30 minutes

3. DPoP (Demonstrating Proof-of-Possession)

RFC 9449 sender-constrained tokens for enhanced security. The DPoP proof binds the token to a specific client key pair, preventing token theft.

Note: DPoP adds a cryptographic proof to each request, ensuring that even if a token is intercepted, it cannot be replayed by another client.

Role-Based Access Control (RBAC)

Role Permissions Description
viewer consent:read, admin:read Read-only access to consent data and admin views
consent-reader consent:read Read consent decisions only
consent-writer consent:read, consent:write Read and write consent decisions
admin All permissions Full access to tenant resources
super-admin All permissions Full access to all resources

Rate Limiting

Two-tier rate limiting using atomic Redis Lua scripts:

Burst Limits requests per 120-second window (e.g., 1,000 requests / 2 min)
Monthly Limits total requests per 35-day billing window (e.g., 100,000 requests / month)

Rate limit headers on every response:

X-RateLimit-Limit: 1000
X-RateLimit-Remaining: 847
X-RateLimit-Reset: 1679900000

When exceeded (429 Too Many Requests):

{
  "requestId": "uuid",
  "error": "RATE_LIMIT_EXCEEDED",
  "message": "Burst rate limit exceeded",
  "retryable": true,
  "retryAfter": 45
}

Request Tracing

Every request gets a unique X-Request-Id header (UUID). This ID appears in all error responses and can be used for support inquiries and log correlation.

Tenant Isolation

Three-layer isolation ensures tenants cannot access each other's data:

1
PostgreSQL

Separate schema per tenant (t_\{tenantId})

2
Redis

Key prefix per tenant, ACL user restrictions

3
Keycloak

Separate realm per tenant with isolated users and roles

TLS Encryption

All connections are encrypted in transit:

PostgreSQL: TLS with certificate verification
Redis: TLS with CA cert support
Keycloak: HTTPS
API: HTTPS (terminate at load balancer or application level)

DSAR Compliance

Immutable audit log for all erasure operations (never deleted)
Cryptographic deletion receipts
GDPR Articles 15 (access), 17 (erasure), 20 (portability) supported
