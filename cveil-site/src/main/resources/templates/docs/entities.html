Data Model

Cveil's data model is organized around a governance hierarchy that connects regulations to the actual data fields they protect.

Overview

The model flows from top-level regulatory requirements down to individual consent records on specific data fields:

Regulation ←──→ Jurisdiction
     ↓ (linked)
   Purpose ←──→ Policy
     ↓ (applied to)
   Category ←──→ Field
                   ↓
                 Entity
                   ↓
             Subject Consent
Note: Each entity below maps to a REST resource with full CRUD operations. The Catalogue API manages entities, fields, and categories. The Governance API manages purposes, regulations, jurisdictions, and policies.

Subjects

A data subject is a person whose personal data is collected and processed. Subjects are the root entity in every consent decision.

Field Type Description
subjectId UUID Unique identifier
subjectName String Unique human-readable name
description String Optional description
createdAt Timestamp When the subject was created
createdBy String Identity of the creator
updatedAt Timestamp Last modification time
updatedBy String Identity of the last modifier

GET POST PUT DELETE /api/v1/subjects

Entities

An entity represents a data source or table in your system — for example, users, orders, or patient_records. Entities are containers for fields.

Field Type Description
entityId UUID Unique identifier
entityName String Unique human-readable name
description String Optional description

GET POST PUT DELETE /api/v1/catalogue/entities

Fields

A field is a specific data column within an entity that contains sensitive data — for example, email, phone, or ssn. Fields can be assigned to one or more categories.

Field Type Description
fieldId UUID Unique identifier
fieldName String Name of the data column
description String Optional description
entity EntityView The parent entity this field belongs to
categories List<CategoryView> Categories this field is classified under

GET POST PUT DELETE /api/v1/catalogue/fields

Categories

Categories classify fields by data sensitivity — for example, PII, PHI, or Financial. Category-level consent applies to every field in that category.

Field Type Description
categoryId UUID Unique identifier
categoryName String Unique classification name
description String Optional description

GET POST PUT DELETE /api/v1/catalogue/categories

Purposes

A purpose defines why personal data is processed — for example, marketing_emails, analytics, or fraud_prevention. Purposes have policies and can be linked to regulations.

Field Type Description
purposeId UUID Unique identifier
purposeName String Unique purpose name
description String Optional description
regulations List<RegulationRef> Linked regulatory frameworks
policies List<PolicyView> Policies defining which data requires consent

GET POST PUT DELETE /api/v1/governance/purposes

Regulations

A regulation is a legal framework that governs data processing — for example, GDPR, CCPA, or HIPAA. Regulations are linked to the jurisdictions where they apply.

Field Type Description
regulationId UUID Unique identifier
regulationName String Unique regulation name
description String Optional description
activeJurisdictions List<JurisdictionView> Jurisdictions where this regulation is enforced

GET POST PUT DELETE /api/v1/governance/regulations

Jurisdictions

A jurisdiction is a geographic region where a regulation applies — for example, EU, California, or United States. Jurisdictions determine which consent rules are active for a given subject.

Field Type Description
jurisdictionId UUID Unique identifier
jurisdictionName String Unique jurisdiction name
description String Optional description

GET POST PUT DELETE /api/v1/governance/jurisdictions

Policies

A policy links a purpose to the data it governs, specifying which fields or categories require consent and what masking strategy to apply when consent is denied. Policies are always scoped to a parent purpose.

Field Type Description
policyId UUID Unique identifier
policyType Enum CATEGORY or FIELD
category CategoryRef Target category (for CATEGORY policies)
field FieldRef Target entity + field (for FIELD policies)

Category Policy

Applies to all fields in the specified category for the parent purpose. Example: "Require consent for all PII fields used in marketing."

Field Policy

Applies to a specific entity + field for the parent purpose. Overrides any category-level policy. Example: "Require consent for users.ssn in fraud prevention."

Consent Scope

The ConsentScope record ties everything together. It represents the intersection of entity, field, category, purpose, and jurisdiction that a consent decision applies to:

{
  "entityName": "users",
  "fieldName": "email",
  "categoryName": "PII",
  "purposeName": "marketing_emails",
  "jurisdictionName": "EU"
}
Flexibility: Any combination of these fields can be provided. A scope with only purposeName applies broadly; a scope with all five fields applies to one specific cell. More specific scopes always override broader ones.
